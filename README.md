## מבנה מסד הנתונים

| טבלה | תיאור |
|---|---|

## שלוש השיטות שמומשו

### 1. Python - `compile()` + `eval()`
כל נוסחה מתקומפלת **פעם אחת** לאובייקט קוד, ולאחר מכן מורצת בלולאה עם `eval()` על כל רשומה בנפרד, בתוך namespace מוגבל (ללא `__builtins__`, רק פונקציות המתמטיקה הדרושות). זו הגישה ה"מפורשת" (interpreted) הבסיסית להשוואה.
>
> **הערה לגבי בטיחות:** הסרת `__builtins__` **מצמצמת** את משטח התקיפה (חוסמת גישה ישירה ל-`import`, `open` וכו') אבל אינה שקולה ל-sandbox אמיתי - עדיין ניתן להגיע לפונקציונליות מסוכנת דרך שרשראות attribute-access על אובייקטים (למשל דרך `().__class__.__bases__`). מכיוון שבפרויקט זה הנוסחאות מגיעות מ-`t_targil` שממולא על ידי `seed_formulas.py` (מקור מהימן, לא קלט חיצוני), הסיכון בפועל נמוך. לשימוש production עם נוסחאות ממקור שאינו מהימן, יש להוסיף אימות מבני (למשל `ast.parse(expr, mode="eval")` עם allow-list של Node types מותרים בלבד - `BinOp`, `UnaryOp`, `Call` לפונקציות מאושרות, `Name` לבין `a,b,c,d` בלבד - ודחיית `Attribute`, `Subscript`, `Lambda` וכו') לפני קריאה ל-`eval()`.

📄 [`solutions/python_eval/solve.py`](solutions/python_eval/solve.py)

### 2. SQL - נוסחה דינמית שמורצת בתוך מנוע מסד הנתונים
במקום למשוך נתונים לתוכנית ולעבור עליהם בלולאה, השיטה בונה **שאילתת SQL דינמית אחת לכל נוסחה** (מקביל ל-`EXECUTE IMMEDIATE`/`sp_executesql` שהוזכרו באפיון - ב-SQLite אין Stored Procedures אז ה"דינמיות" ממומשת על ידי בניית מחרוזת ה-SQL בזמן ריצה והרצתה ישירות) ומפעילה אותה פעם אחת על כל הטבלה. הפונקציות `sqrt/log/power` נרשמות כפונקציות מותאמות אישית ל-SQLite כדי להבטיח זמינות בכל סביבה.

📄 [`solutions/sql_native/solve.py`](solutions/sql_native/solve.py) (הרצה) · [`solutions/sql_native/formula_translator.py`](solutions/sql_native/formula_translator.py) (Tokenizer + Parser שמתרגם את התחביר המשותף לטקסט SQL - נחוץ כי `^` חייב להפוך ל-`power(x,y)`, ותת-הביטויים משני צידי `^` יכולים להיות מורכבים, למשל `(a+b)^2`, ולא רק שם שדה בודד; regex פשוט לא מספיק לזה)

**הערה לגבי הפער ממה שהאפיון תיאר:** האפיון מתאר Stored Procedure עם `EXECUTE IMMEDIATE`/`sp_executesql` בתוך מסד נתונים כמו Oracle/SQL Server. נבחר SQLite (ראו "רקע ומבנה הפרויקט" למעלה) בדיוק כדי לאפשר קובץ יחיד שניתן להריץ ולשחזר בקלות מוחלטת בכל מחשב וב-GitHub - אבל אין ל-SQLite Stored Procedures בכלל. לכן ה"דינמיות" כאן ממומשת בפייתון: בניית מחרוזת SQL בזמן ריצה מתוך הנוסחה, והרצתה. הרעיון המרכזי (הנוסחה לא מקובעת בקוד, אלא נלמדת מהטבלה ומתורגמת ל-SQL בזמן ריצה, ומנוע ה-DB הוא זה שמבצע את החישוב בפועל) זהה; מה שאין הוא ה-`CREATE PROCEDURE` עצמו. כך זה היה נראה עם SQL Server אמיתי (קוד להמחשה בלבד, לא רץ בפועל בפרויקט זה):

```sql
CREATE PROCEDURE dbo.ComputeFormula (@TargilId INT, @Method VARCHAR(50))
AS
BEGIN
    DECLARE @sql NVARCHAR(MAX);
    DECLARE @targil VARCHAR(200), @tnai VARCHAR(200), @falseTargil VARCHAR(200);

    SELECT @targil = targil, @tnai = tnai, @falseTargil = targil_false
    FROM t_targil WHERE targil_id = @TargilId;

    -- בניית ה-SQL הדינמי מתוך הנוסחה (התרגום a+b -> a+b, ^ -> POWER(...) וכו'
    -- נעשה כאן באפליקציה שקוראת ל-Stored Procedure, בדיוק כמו ב-formula_translator.py)
    SET @sql = N'INSERT INTO t_results (data_id, targil_id, method, result)
                 SELECT data_id, @TargilId, @Method,
                        CASE WHEN ' + @tnai + N' THEN ' + @targil + N' ELSE ' + @falseTargil + N' END
                 FROM t_data';

    EXEC sp_executesql @sql, N'@TargilId INT, @Method VARCHAR(50)', @TargilId, @Method;
END
```

ההבדל המהותי מהמימוש בפועל (`formula_translator.py` + `sqlite3.execute`): ב-SQL Server, `sqrt`/`log`/`POWER` הן פונקציות **native** של המנוע (מבוצעות ב-C++ בתוך ה-DB, ללא קפיצה חזרה לשפת אפליקציה) - בניגוד ל-SQLite כאן, שבו נאלצנו לרשום אותן כפונקציות Python מותאמות אישית (ראו התובנה בהמשך למטה, תחת "תוצאות ביצועים").

### 3. C# - מפענח נוסחאות (Parser) עצמאי
נכתב Tokenizer + Parser (recursive descent) + מעריך AST ב-C# טהור, ללא ספריות חיצוניות לחישוב (`Microsoft.Data.Sqlite` משמש רק לגישה למסד הנתונים). כל נוסחה נפרסת **פעם אחת** לעץ תחביר, ולאחר מכן העץ מוערך עבור כל רשומה - המקבילה של .NET ל"קומפל פעם, הרץ הרבה" של Python, אך עם קוד מנוהל (managed, JIT-compiled) במקום פרשן (interpreter).

📄 [`solutions/csharp_solution/Formula.cs`](solutions/csharp_solution/Formula.cs) (הפרסר) · [`solutions/csharp_solution/Program.cs`](solutions/csharp_solution/Program.cs) (הרצה)

> למה לא `DataTable.Compute` או ספריה כמו NCalc, כפי שמוצע באפיון? `DataTable.Compute` לא תומך בפונקציות כמו `sqrt`/`log`/חזקה שנדרשות בנוסחאות המורכבות. נכתב פענוח עצמאי כדי לתמוך בכל התחביר המשותף בלי תלות בספריה חיצונית שאין ודאות לגבי חתימות הפונקציות שלה.

## איך מריצים את הכל

כל הפקודות הן PowerShell, מריצים מתיקיית השורש של הפרויקט אלא אם צוין אחרת.

### 1. יצירת מסד הנתונים ומילויו

```powershell
cd db
python init_db.py --db ..\payments.db --rows 1000000   # להרצה מהירה בפיתוח אפשר --rows 1000
```

יוצר מחדש את 4 הטבלאות, ממלא את `t_targil` ב-12 הנוסחאות, וממלא את `t_data` במיליון רשומות רנדומליות (a,b,c,d בטווח 1-1000, ב-batches של 50,000 לביצועים).

### 2. הרצת שלוש השיטות

```powershell
# Python
cd solutions\python_eval
python solve.py --db ..\..\payments.db

# SQL דינמי
cd ..\sql_native
python solve.py --db ..\..\payments.db

# C#
cd ..\csharp_solution
dotnet run -- --db ..\..\payments.db
```

כל שיטה: מוחקת את התוצאות הקודמות שלה מ-`t_results`/`t_log`, עוברת על כל 12 הנוסחאות, מחשבת את התוצאה עבור **כל** מיליון הרשומות, ושומרת את התוצאות + זמן הריצה הכולל לכל נוסחה.

### 3. השוואת תוצאות ובדיקת עקביות

```powershell
cd scripts
python compare_results.py --db ..\payments.db
```

מוודא (בעזרת שאילתת SQL אחת, כדי להישאר יעיל גם על עשרות מיליוני שורות) ששלוש השיטות הניבו בדיוק אותה תוצאה עבור כל שילוב של רשומה+נוסחה, ומדפיס טבלת השוואת זמנים.

### 4. הפקת נתוני הדוח והרצת מסך הדוח

```powershell
cd scripts
python generate_report_data.py --db ..\payments.db

cd ..\report

```

### 5. בדיקות אוטומטיות (unit tests)

```powershell
# פרסר ה-SQL (formula_translator.py) - 24 בדיקות עם pytest
cd solutions\sql_native
python -m pip install pytest    # פעם ראשונה בלבד

# פרסר ה-C# (Formula.cs) - 19 בדיקות עם xUnit

```

שני הפרסרים העצמאיים (`formula_translator.py` ל-SQL, `Formula.cs` ל-C#) נכתבו מאפס עבור הפרויקט הזה, אז יש להם כיסוי בדיקות ייעודי - קדימות אופרטורים (`a + b * 2`), סוגריים, אסוציאטיביות ימנית של חזקה (`2^3^2`), מינוס אונרי לצד חזקה (`-2^2`), `sqrt`/`log`/`abs`, ענפי תנאי אמת/שקר, נוסחה לא חוקית, משתנה לא מורשה, וחלוקה באפס - כולל תיעוד מפורש שההתנהגות בחלוקה באפס **שונה בין המנועים** (SQLite מחזיר `NULL`, Python זורק `ZeroDivisionError`, C# מחזיר `Infinity`/`NaN` לפי IEEE 754); זו מגבלה ידועה של ההשוואה ולא בחירת עיצוב מכוונת - ראו פירוט תחת [הערות מתודולוגיה](#הערות-מתודולוגיה-ומגבלות-ידועות). שיטת ה-Python הבסיסית (`python_eval/solve.py`) לא כוללה בדיקות נפרדות כי היא לא מכילה פרסר משלה - היא מסתמכת על `eval()` המובנה של Python, שהתחביר וסדר הפעולות שלו כבר נבדקים על ידי Python עצמו.

בדיקות אלו משלימות את `compare_results.py` (למעלה) ולא מחליפות אותו: הבדיקות האוטומטיות מוודאות **נכונות של כל פרסר בבידוד** על מקרי קצה ידניים; `compare_results.py` מוודא **הסכמה בין שלושת המנועים** על המיליון רשומות + 12 הנוסחאות בפועל.

## תוצאות ביצועים

הרצה מלאה על **1,000,000 רשומות × 12 נוסחאות × 3 שיטות**. `compare_results.py` אימת ש-3 השיטות מניבות **תוצאה זהה** עבור **כל 12,000,000** השילובים (data_id × targil_id), כולל 5,000 הרשומות עם `a==c` שמבטיחות כיסוי אמיתי לענף ה-true של נוסחה 11 (ראו [הערות מתודולוגיה](#הערות-מתודולוגיה-ומגבלות-ידועות)) - ראו את [מסך הדוח](#מסך-הדוח) לתצוגה אינטראקטיבית.

| 9 | `if(a>5) b*2 else b/2` | 0.258 | 1.846 | 2.710 |
| 10 | `if(b<10) a+1 else d-1` | 0.169 | 2.734 | 1.784 |
| 11 | `if(a==c) 1 else 0` | 0.135 | 1.579 | 1.263 |
| 12 | `if(c>d) sqrt(a²+b²) else \|a-b\|` | 0.350 | 2.983 | 3.164 |

**תובנה מעניינת:** לשיטת ה-SQL אין יתרון גורף כאן, ולפעמים היא אף האיטית ביותר - למרות ש"מריצים שאילתה אחת שמחשבת הכל". הסיבה: `sqrt`, `log` ו-`power` נרשמו כפונקציות Python מותאמות אישית (`create_function`) כי SQLite הבסיסי לא כולל אותן תמיד - כך שבפועל, לכל שורה יש קפיצה חזרה למפרש Python בכל קריאה לפונקציה כזו (רואים זאת בבירור בנוסחאות 6 ו-12, האיטיות ביותר גם ב-SQL). בנוסחאות עם אופרטורים בסיסיים בלבד (+,-,*,/, השוואות) שמנוע ה-SQLite מבצע באופן טבעי לגמרי בתוך C, הזמן דומה או טוב יותר מ-Python. עם driver המספק פונקציות מתמטיקה native (כמו PostgreSQL/SQL Server), הציפייה היא שהשיטה הזו הייתה מנצחת בבירור.

## מסך הדוח

מסך הדוח נבנה ב-**Angular** (`report/`) וקורא קובץ JSON סטטי (`report/public/report-data.json`) שמופק על ידי `scripts/generate_report_data.py` - כך שאין צורך בשרת backend חי כדי להציג את ההשוואה; אפשר להעלות את תוצאת ה-build (`npm run build` → `report/dist/report`) לכל שירות אחסון סטטי (GitHub Pages, Netlify, Vercel וכו').

המסך מציג:
- באדג' אימות שכל השיטות מניבות תוצאות זהות
- גרף עמודות המשווה זמן ריצה כולל בין השיטות
- הסבר קצר על כל שיטה
- טבלה מפורטת עם זמן ריצה לכל נוסחה בכל שיטה

## מסקנות והמלצה

**השיטה המהירה והחכמה ביותר במבחן הזה: C# עם מפענח נוסחאות (parser) עצמאי.**

מדוע:
- **קומפילציה חד-פעמית + הערכה native**: הנוסחה נפרסת פעם אחת לעץ תחביר, ולאחר מכן כל הרצה היא הליכה על עץ אובייקטים בקוד מנוהל שרץ תחת ה-JIT של .NET - אין תקורת פירוש (interpretation) חוזרת כמו ב-Python, ואין קפיצות בין מנועים כמו ב-SQL עם UDFs.
- **פי ~10-12 מהיר יותר** משתי השיטות האחרות (ראו טבלת "תוצאות ביצועים" למעלה), על כל סוגי הנוסחאות (פשוטות, מורכבות ותנאי).
- מדרגת היטב: ההפרש בין נוסחה פשוטה למורכבת קטן משמעותית ב-C# לעומת Python/SQL.

**מתי בכל זאת לשקול את השיטות האחרות:**
- **Python (`eval`)** - הכי מהיר לפתח ולתחזק (כמעט אפס קוד תשתית), ומספיק מהיר לרוב מקרי השימוש (עדיין ~1.3-2.4 שניות למיליון רשומות בנוסחה בודדת - כלומר מיליוני חישובים בשנייה). מתאים כשפשטות הפיתוח חשובה יותר מהביצועים המקסימליים.
- **SQL דינמי** - היתרון האמיתי שלו לא מודגם כאן במלואו, כי SQLite נאלץ "לשאול" את Python בכל קריאה לפונקציה מתמטית. במסד נתונים "אמיתי" עם מנוע SQL מלא (PostgreSQL, SQL Server, Oracle) שבו `sqrt`/`log`/`power` הן פונקציות native במנוע (בלי לחצות בחזרה לשפת אפליקציה), הציפייה הסבירה היא שהחישוב יתבצע קרוב לחומרה (כמו C++) ויתחרה ישירות ב-C#, עם היתרון הנוסף שהחישוב קורה היכן שהנתונים כבר יושבים (ללא Network/IO של משיכת מיליון שורות לאפליקציה) - יתרון גדול עוד יותר במערכת אמיתית עם בסיס נתונים מרוחק.

**המלצה מעשית למערכת תשלומים אמיתית:** אם הביצועים קריטיים ונפח הנתונים גדול - לממש את מנוע החישוב הדינמי כמפענח נוסחאות ייעודי (כמו כאן) בשפה מקומפלת (C#/.NET, Java, Go...), שנטען וקומפל את הנוסחה פעם אחת (עם cache) ומריץ אותה על כל הרשומות. Python מתאים לסביבת פיתוח/prototype מהירה. SQL דינמי כדאי כשרוב הלוגיקה ניתנת לביטוי באופרטורים בסיסיים שהמנוע תומך בהם באופן native (לא UDF), ובמיוחד כשרוצים להימנע מלהוציא נתונים ממסד הנתונים כלל.

## הערות מתודולוגיה ומגבלות ידועות

שקיפות מלאה לגבי כמה החלטות מודעות ומגבלה אחת שתוקנה, כדי שברור מה בדיוק נמדד ומה הגבולות של ההשוואה:

1. **SQLite כתחליף למסד נתונים "אמיתי"** - ראו ההערה המפורטת (כולל דוגמת קוד ל-SQL Server) תחת "שלוש השיטות שמומשו" למעלה. אין ב-SQLite Stored Procedures, אז אין `CREATE PROCEDURE` בפועל בפרויקט - רק בניית SQL דינמי והרצתו.

2. **א-סימטריה מכוונת במדידת הזמן של השיטה ה-SQL:** ב-Python וב-C# הנתונים (מיליון השורות) נטענים לזיכרון **פעם אחת מראש, מחוץ לתזמון**, והלולאה הפנימית מודדת חישוב טהור בלבד. ב-SQL, הזמן הנמדד (`t_log.run_time`) כולל גם את ה-`fetchall()` - כלומר גם את שליפת מיליון התוצאות בחזרה מ-SQLite אל תוך Python. זו החלטה מודעת, לא פספוס: כדי לשמור את התוצאה ב-`t_results` חייבים להוציא אותה מהמנוע בסופו של דבר, בכל שלוש השיטות - כך שזו עלות אמיתית ובלתי נמנעת של "להשתמש בגישה הזו" ולא רק תקורת מדידה מלאכותית.

3. **כיסוי הענף `a==c` בנוסחה 11:** `a` ו-`c` הם floats רנדומליים בלתי-תלויים, כך שבאופן טבעי `a == c` כמעט לעולם לא מתקיים (הסתברות ~0). כדי שהענף ה-true של הנוסחה הזו (`if(a==c) 1 else 0`) באמת ייבדק ולא ירוץ "בעיוור" על מיליון שורות שכולן נופלות לענף ה-false - [`db/seed_data.py`](db/seed_data.py) מגדיר במפורש `c := a` באחת מכל 200 רשומות (5,000 רשומות מתוך המיליון). `compare_results.py` אימת ששלוש השיטות מסכימות במדויק גם על הרשומות האלה (תוצאה 1.0) וגם על כל השאר (תוצאה 0.0).

4. **תוקן: פירוק ביטויים מקוננים סביב `^`.** בגרסה מוקדמת יותר, תרגום `^` ל-SQL (`power(x,y)`) נעשה עם regex פשוט (`(\w+)\^(\w+)`) שתפס רק טוקן בודד בכל צד - נוסחה כמו `(a+b)^2` הייתה נפרסת שגוי. תוקן על ידי כתיבת Parser אמיתי ([`formula_translator.py`](solutions/sql_native/formula_translator.py)) שמטפל בכל קינון. באופן דומה, המפענח ב-C# ([`Formula.cs`](solutions/csharp_solution/Formula.cs)) תוקן כך ש-unary minus לצד `^` יתנהג כמו במוסכמה המתמטית/כמו ב-Python (`-a^2` שווה ל-`-(a^2)`, לא ל-`(-a)^2`) - אף אחת מ-12 הנוסחאות הקיימות לא כללה `^` על ביטוי מקונן או unary minus לצד `^`, כך שהבאג לא השפיע על שום תוצאה בפועל, אבל שני התיקונים חשובים לתמיכה נכונה בנוסחאות עתידיות.

5. **חוסר עקביות בין המנועים בהתנהגות חלוקה באפס.** שלוש השיטות אינן מתנהגות אותו הדבר בחלוקה באפס: SQLite מחזיר `NULL`, Python (`solve.py`) זורק `ZeroDivisionError`, ו-C# מחזיר `Infinity`/`NaN` (לפי תקן IEEE 754). זו מגבלה ידועה של ההשוואה, לא בחירת עיצוב מכוונת - הנתונים הנוכחיים (`d` בטווח 1-1000 בנוסחה `d/4`) אינם מייצרים מכנה אפס באף אחת מ-12 הנוסחאות, כך שהפער לא נחשף בהרצה הקיימת ואינו משפיע על תוצאות ההשוואה. לא מומש מנגנון לאיחוד ההתנהגות בין המנועים - מחוץ להיקף המדידה הנוכחית.
